Grok Bot：12 頁看懂 Agent 團隊架構

本講稿對應固定滿版的 12 頁流程圖。內容選編自傑少 JAY 的影片，重點是責任、資料與產物如何接力；不包含帳號、安裝、付費或變現操作。圖形是教學重構，不是產品內部系統規格。

1｜架構總覽：先分清責任

先看左邊的人：由我們定目標與做最後決定。中間的管理層由 Gummy 統籌，再分給信件、專案與行銷主管。右邊的執行 Agent 使用工具、交出成果。虛線表示結果必須回來被驗收，不是交辦完就不管。

2｜三層責任：決策、管理、執行

人負責方向與重要取捨，主管負責拆任務、分派與驗收，執行者負責讀資料、創作或更新系統。箭頭向下交辦，結果向上回報。如果主管仍包辦全部執行，這個分層就只剩名字不同。

3｜能力組成：背景、工具與流程

Context 告訴 Agent 公司做什麼、目標與成功標準。Tools 讓它讀資料與操作服務。Workflow 安排觸發時機、執行順序與協作。原片使用 Connectors 與 Automation 等詞，這裡用工具與流程概括，方便理解。

4｜共享脈絡：資料不足就先補

網站、共同目標與營運證據先匯入工作脈絡，再問資料是否足夠。如果足夠才做判斷；不足就走下方的補件迴圈。原片以招滿一百位學生為目標，但只有公司網站，仍不足以分析完整招生與成交狀況。

5｜單一窗口：你只對接 Gummy

你給 Gummy 一次需求，由它找各部門協作，再統一回報。不要讓每個 Bot 都各自丟一份結果給你。原片群組曾因多人同時發言變得混亂，所以多 Agent 除了增加能力，也會增加協調成本。

6｜信件案例：看一次完整委派鏈

從你交辦週報開始，Gummy 找 Coco，Coco 再分派信件執行者。執行者讀取 Gmail、整理分類與待辦，產出試算表；再經主管檢查，向上回報。驗收要看實際產物，不只接受聊天中的「已完成」。

7｜跨部門交接：會議接成專案

Plaud 會議記錄交給 Mochi，分成知識與決策，以及需要執行的待辦。待辦交給 Kiwi，對照飛書討論後更新 ClickUp。這裡最重要的是交接產物清楚：Mochi 不只做摘要，Kiwi 也不只是重複另一份摘要。

8｜共用工作環境：檔案路徑也要管理

多個 Bot 共用工作環境，就需要一致的背景、專案與報告位置。原片第一次只建資料夾，仍有散落檔案；再次歸位後，也要通知各角色改用新路徑。檔案有分類，不代表已建立權限隔離，也不能保證消除幻覺。

9｜行銷團隊：主管分派，執行者交稿

Sunny 決定方向，Peach 交長影音企劃，Lemon 交短影音腳本，Mango 交文字，Tarot 交圖片與影片。四路成果最後匯回 Sunny 驗收。先用一篇稿、一張圖或短片測試分工；能交初稿，不代表行銷成效已經成立。

10｜Bot、工作方法、工具與模板

Bot 是誰負責，SOP 或 Skill 是照什麼方法做，工具是用什麼完成工作，模板則打包設定方便重用。原片先只有四份行銷 SOP，後來才建立四個獨立 Bot。不要把四份規則當成四個角色，也不要把規則調整當成模型權重訓練。

11｜控制點：重要動作與成果都要檢查

先判斷任務風險，高風險動作由人確認，再交給執行者。產物還要通過驗收；不通過就修正或由人接手。這頁是依片中卡點歸納的建議，不代表產品已內建同樣的風險判斷與完整驗收系統。

12｜收束：先讓一條工作流可靠

最後把目標、主管分派、執行者交產物與驗收修正接成閉環。成果的問題要更新回規則與背景。先問每個角色收到什麼、交出什麼、由誰驗收，再決定要開幾個 Agent。先跑通一條小流程，再擴大團隊。
