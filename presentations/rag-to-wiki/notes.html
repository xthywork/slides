為什麼大量資料會讓 RAG 找不到正確答案？｜講稿大綱

12 頁，分為問題與限制、故障案例、LLMWiki 解決思路、比較與總結。資料量、事件、文件及相似度均為假設教學情境；相似度不是答案正確率。

1. 為什麼資料量越大，RAG 越可能找不到正確答案？

以訂單 API 故障案例帶入：資料庫明明有根因文件，但單次 Top-K 檢索可能把它留在名單外。接著看 LLMWiki 如何在資料整理階段，先建立事件與原因的關係。全篇比較常見的單次向量片段檢索與 Wiki 式知識管理，不把所有 RAG 都視為同一種設計。

本頁重點：從「找得到相關文件」，走向「讀得到真正原因」。

2. RAG 為什麼會找不到資料？

Top-K 指這次選取排名前 K 筆。資料庫可以很大，但模型這次閱讀的內容只是一部分。資料量增加本身不保證失敗，風險來自相似候選增加、排名與固定取回名額的交互作用。

本頁重點：資料有保存，不代表這次回答一定讀得到。

3. 大量資料造成的五大問題

依序說明五個環節。Embedding 把內容壓縮成向量，不能完整保留所有條件；更多相似候選會競爭固定 Top-K；Chunk 可能切斷前後文和跨段關係；模型上下文及處理預算有限；重複、舊版、無關資料也會影響排名。增加 K 可找回部分資料，但同時增加上下文、成本與雜訊，不能保證解決所有問題。

本頁重點：要檢查整條路：表示、候選、切分、上下文與資料品質。

4. 核心問題：語意相似不等於正確答案

把相關性與答案充分性分開。一份文件大量重複「API 逾時」，可能只描述症狀；寫「付款閘道連線池」的變更紀錄才包含根因，但用字與提問比較不同。接下來以 Top-5 與 Top-6 的固定示意案例展示這個缺口。

本頁重點：相似度可以排序資料，不能直接當成答案正確率。

5. 案例背景：訂單 API 大量逾時

這是虛構教學案例，不是真實事故或效能測試。公司有一百萬筆不同來源資料，使用者問的是 8 月 15 日下午的訂單結帳 API 逾時。這次向量檢索固定只取 Top-5；根因放在 CHG-2841 部署變更紀錄。

本頁重點：同一個問題、同一批資料，先看原因文件會不會入選。

6. Top-5 都相關，卻沒有真正答案

依序展示六份文件和假設相似度：故障報告 96%、回應時間監控 94%、504 錯誤分析 93%、客服紀錄 91%、事件摘要 89%、CHG-2841 85%。在第五筆畫截止線，說明第六筆沒有進入模型。這些分數是人為設定的相似度示意，不是機率、答案正確率或實測結果。點文件可查看同一組虛構記錄。

本頁重點：正確文件排 Top-6，系統卻只把 Top-5 交給 LLM。

7. 為什麼真正的答案被排除？

使用相同的六份資料，解釋排序缺口。不要把向量搜尋說成只數關鍵字：Embedding 衡量語意，但仍可能因描述角度、術語及內容壓縮而錯排。前五筆是症狀，第六筆談付款閘道設定。LLM 沒拿到這份原因文件時，不應憑空補出根因。

本頁重點：高分文件占滿名額，原因文件就可能留在上下文之外。

8. LLMWiki：從文件搜尋轉向知識整合

這裡展示建議的 Wiki 式整理流程。以本例六份關聯文件示意，不表示把一百萬筆資料一次放進模型。可逐份或分批匯入、更新事件頁與相關概念。重要的是把症狀、原因與證據留下交叉連結；這些關係也能以 Markdown 連結實作，不一定要使用圖形資料庫。產品與工作流程仍需正確辨認關聯。

本頁重點：把關聯建立提前，讓下次查詢可以從整合好的知識開始。

9. Wiki：8/15 訂單 API 故障事件

展示保存好的事件頁。現象是訂單結帳 API 大量逾時、504 錯誤。根因是 CHG-2841 部署時，付款閘道連線池上限從 200 誤設為 20；在本例負載下，可用連線不足使請求阻塞。故障、監控、客服及部署記錄都連回原始文件。頁面為本地教學示意，不是連接真實 LLMWiki 服務。

本頁重點：把「故障現象」與「根本原因」整合成同一個知識脈絡。

10. 相同問題，兩條查詢路徑

用同一個問題並排兩條流程。單次 RAG 路徑到原始文件 Top-5，只拿到現象；Wiki 路徑到事件頁，可沿預先保存的關聯讀到 CHG-2841。這不是取消檢索，也不是保證任何 Wiki 都較準，而是把搜尋單位從孤立片段提升為已整理的知識主題。

本頁重點：Wiki 讓原因跟著事件一起被查到，降低跨文件答案遺漏風險。

11. 傳統 RAG 與 LLMWiki 比較

保留五個比較面向：資料組織、知識關聯、搜尋目標、跨文件推理、Top-K 影響。這裡的傳統 RAG 指單次原始片段檢索；進階 RAG 也能做多輪查詢、階層摘要、關係圖或混合檢索。LLMWiki 也會漏檢或整合錯誤，仍需要來源、更新、查核與檢索設計。兩者可結合。

本頁重點：成立前提：整理時關係正確，查詢時找對知識頁，並持續維護來源。

12. 從找到相關資料，到找到真正答案

回到 CHG-2841 收尾：Top-5 的高分現象文件，不保證提供根因。Wiki 式知識管理先把事件與付款閘道設定連起來，讓下一次問事件時，能沿概念頁讀到原因。核心是預先整理並保存關係，仍需正確的檢索、維護及證據查核。

本頁重點：RAG 檢索相關內容；LLMWiki 進一步整理內容間的關係，讓答案更容易被找到。
